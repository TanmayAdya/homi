# Shared contracts v1

These files define the first Flutter/backend handoff. The schemas use JSON Schema 2020-12. Configure a full validator to assert `format` checks when adopting one; the dependency-free Dart tests cover the subset currently used here.

- `case.schema.json`: case/profile, reviewed findings, and measurements. Required nullable fields use explicit `null` for unknown. Zero and false are known values. `ownerConsentReported` records an answer, not verified permission. Evidence IDs refer to private evidence records; the fixture does not contain real photos.
- `match.schema.json`: explained results returned by the matcher/API. The Dart models validate structure and source references; they do not evaluate eligibility. `evaluationDate` is an explicit input to the server's policy evaluation, while `evaluatedAt` records when it ran. `recheckAfter: null` means the cache cannot establish freshness. Rule updates can invalidate a result earlier than its deadline.
- `match-request.schema.json`: authenticated saved-case request with case ID and expected revision; no client-supplied owner, policy, profile or clock.
- `case-read-request.schema.json`: authenticated case reload by ID, returning the current `case.schema.json` snapshot so an uncertain answer save can be recovered without guessing its new revision.
- `case-list-request.schema.json` and `case-list.schema.json`: authenticated discovery of minimal owned case IDs/revisions, with a 1–20 item limit and exclusive ID boundary. Runtime parsing additionally verifies UTF-8 byte order, uniqueness, request-bound limits and continuation consistency.
- `request-tracking-read-request.schema.json`, `request-tracking-append-request.schema.json` and `request-tracking.schema.json`: private manually reported request events, independent request revisions, explicit source/next-action/responsible-party fields and exact UUIDv4 retry identity. Runtime additionally enforces contiguous event revisions, unique IDs, monotonic recorded time/case revisions, real dates and occurrence dates no later than recording. These records never verify submission, agency receipt, eligibility or approval.
- `api-error.schema.json`: safe API error envelope and supported HTTP/error-code pairs. Client messages come from local constants, not raw server details.
- `packet-request.schema.json`: authenticated draft-preparation request selecting a program and a retry key; the server selects rules and loads the saved case.
- `packet.schema.json`: implemented draft-only checklist response. Unknown form/mapping/storage fields remain null until verified or generated. A draft is never proof of submission or approval.
- `form-answers.schema.json`: separate case/form-bound administrative answers, server-owned review provenance, independent answer revision and explicit freshness. This is not a clinical, consent or signature record.
- `form-answers-read-request.schema.json` and `form-answers-save-request.schema.json`: owner-scoped reads and full replacements; saves require expected case/answer revisions and full form context. Every successful save advances the case revision to invalidate old results.
- `evidence.schema.json`, `evidence-list-request.schema.json` and `evidence-download-request.schema.json`: private sanitized image catalog and authenticated PNG preview. Catalog and individual evidence revisions are separate from case revisions; metadata has no storage paths or URLs.
- `draft-export.schema.json`, `draft-export-request.schema.json` and `draft-export-download-request.schema.json`: explicit reviewed image selections, private draft artifact metadata and authenticated PDF download. The artifact remains a draft. Its 15-minute operational expiry never establishes benefits-policy freshness.
- `fixtures/packets.json`: three fictional saved checklists corresponding to the case/match scenarios. They contain no official forms or real evidence files.
- `fixtures/scenarios.json`: three prewritten, entirely fictional scenarios. The example route checks only `Demo City` and `Example Plan`. These values are teaching data with no real program sources, intake, or benefit policy. No live matcher, backend, or PDF generator is included in the fixtures.

The Dart boundary in `lib/shared/models/contracts.dart` rejects unsupported schema versions, missing/extra fields, invalid types, dates and enums, and inconsistent references. Lists are immutable after parsing. The asset adapter in `lib/shared/services/demo_scenario_service.dart` reads the shared JSON for the first UI demo.

Fixture dates are deliberately fixed for repeatability. At or after their recheck deadline they are stale; tests provide explicit times, and a UI showing them should retain the demo label rather than calling them current program advice.

Run `flutter test test/contracts` from the application root. These tests check the fictional fixture handoff, unknown/zero/false handling, malformed data, source references, and case/date freshness boundaries. They do not validate any real program rule.

`flutter test test/services` checks the request/error schemas and mobile clients. Packet parsing also rejects duplicate checklist/evidence IDs and unsafe storage references; the client checks attachment membership against the requested case. The complete executable handoffs are documented in [matching-api.md](../../docs/matching-api.md) and [packet-api.md](../../docs/packet-api.md).

The administrative answer model is `lib/shared/models/form_answers.dart`; the read/save/reload client is `lib/shared/services/form_answers_api_client.dart`. Its tests separately check JSON Schema conditional/array constraints and runtime cross-field invariants. Form save requests replace all answers; omitted keys clear them. `FORM_SAVE_UNCERTAIN` is a local client error, not a server code: reload the case, then its answers before deciding on another save. Run `dart run tool/check_form_answers_api.dart --backend ../safe-at-home-backend/backend` for the fictional real-HTTP round trip, concurrency, clearing and lost-response recovery check. The backend branch's `docs/form-answers-api.md` describes the adapter and UI handoff; combine that branch before using these endpoints.

Private export models are in `lib/shared/models/evidence.dart` and `draft_export.dart`; `DraftExportApiClient` downloads bounded bytes, validates their SHA-256 against metadata, and refuses late responses after selection changes. It never saves files or invokes platform sharing. The UI must show sanitized images for review before creating `EvidenceSelection` records, then show the full PDF and outstanding checklist. An uncertain export creation may be retried explicitly with the exact same generation key and inputs. Run `dart run tool/check_draft_export_api.dart --backend ../safe-at-home-backend/backend` for the fictional real-HTTP workflow. Backend adapter responsibilities, privacy limits and remaining integration work are in that branch's `docs/evidence-export-api.md`.

Case creation/full replacement and private image upload/deletion now have request/response schemas, `CaseDraft` and `EvidenceUploadResponse`/`EvidenceDeleteResponse` models, and `CaseEvidenceApiClient`. The complete server protocol is `docs/case-evidence-api.md` in the backend branch. The executable mobile handoff is `tool/check_case_evidence_api.dart`. Creation uses a retained random UUIDv4 and assigns revision one; saving requires the expected case revision and returns the complete replacement at the next revision. Save the finding/evidence link before uploading. Photo mutations advance catalog/asset revisions and invalidate exports; they do not advance case revision. Active uploaded links cannot be removed by a case save until explicitly deleted. A deleted evidence ID cannot be restored through the public API.

`CASE_SAVE_UNCERTAIN` and `EVIDENCE_SAVE_UNCERTAIN` are local client recovery states, not server error codes. Reload the retained case ID after uncertain creation/save; reload the case/catalog and inspect the sanitized image after uncertain upload/deletion. Never automatically resend a write or guess its new revision. Keep unsaved edits separately and pass live state callbacks. The new client accepts only fixed same-origin endpoints and bounded bytes. Case-write text rejects NUL (U+0000), blank-only text and lone surrogates at the runtime boundary; other valid text is preserved. Mobile screens and typed deletion integration remain separate work. The backend branch supplies PostgreSQL/Supabase Auth and durable deletion APIs; its `docs/durable-storage-auth.md` and `docs/retention-and-deletion.md` cover setup and limits.

`CaseDiscoveryApiClient` in `lib/shared/services/case_discovery_api_client.dart` lists owned saved-case summaries and resumes the latest complete snapshot through the existing read-case endpoint. Pass an `isCurrent` callback that checks the captured session/account epoch and request generation. Invalidate it on sign-out, account switch, refresh, a newer request or cancellation. For resume, supply the selected list item's `caseRevision` as `minimumCaseRevision`, plus live selected-ID/current-snapshot callbacks; the client rejects regression below both list and current local revisions. Returned data never changes app state automatically. A list is a live traversal in stable UTF-8 case-ID order, not a recency ranking or frozen snapshot; refresh from null to discover inserts before the boundary. Use `dart run tool/check_case_discovery_api.dart --backend ../safe-at-home-backend/backend` for the actual HTTP handoff, also included in verification scope `all`. The backend branch's `docs/case-discovery-api.md` gives exact requests and privacy/recovery behavior.

`RequestTrackingApiClient` in `lib/shared/services/request_tracking_api_client.dart` reads and appends manual reports for one saved case/program. Use immutable `ReadRequestHistoryRequest` and `PendingRequestUpdate` values from `lib/shared/models/request_tracking.dart`; keep the pending object until reconciled. Pass live case, selected-program and current-history callbacks plus `isCurrent` capturing account/session and request epochs. Invalidate that epoch permanently on account change, selection change, cancellation or a newer request. The client bounds responses to 256 KiB and the whole token/request deadline to 15 seconds, rejects revision regression and never retries or modifies local state.

`REQUEST_UPDATE_UNCERTAIN` means an append may have persisted: explicitly read the current case and then its request history, and call `history.acknowledges(pending)` to compare the original update ID, full content, position and case revision. This also works after a later case edit; use the new revision for the read while retaining the original pending object. If absent or different, keep the user's unsaved report and resolve conflicts before explicitly deciding on another write. An unchanged exact retry may return later events as well; never require the final event to be the pending one. Display the history as **user reported**, including `document` or `program_contact` source claims. The latest *recorded* event determines the latest report; occurrence dates may be backdated. `tool/check_request_tracking_api.dart` exercises the fictional real-HTTP handoff and is included in verification scope `all`. The backend branch's `docs/request-tracking-api.md` describes persistence and operational boundaries.

Hosted endpoints can return `429 RATE_LIMITED` before application work is dispatched. Limits are shared by a verified account across access-token rotation; changing an IP/header does not select a separate account. A valid positive integer `Retry-After` header becomes `MatchingApiException.retryAfter` (a `Duration`, at most one hour). Missing, duplicate, date-form, malformed or larger values are ignored. These values are advisory: all seven API clients retain their existing no-automatic-retry behavior and use a local safe message. Keep the same pending update, case edits, image selection and generation key while waiting; a rejection is not a saved result. Invalid error envelopes still follow existing uncertain-write recovery.

Shared service saturation continues to return `503 SERVICE_UNAVAILABLE`; a save/update may still require its existing reload-and-reconcile flow because this status is also used for failures during persistence. Do not treat a retry delay as proof that a write failed. `507 STORAGE_LIMIT_REACHED` is also accepted by `PacketApiClient`: contact the operator, retain the original draft attempt, and do not spin on fresh generation keys. The backend branch documents exact deployment limits; typed mobile account-deletion integration is still separate work.
